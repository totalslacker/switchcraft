# ADR 013 — Reference fixture provenance and regeneration policy

**Status**: Accepted
**Date**: 2026-04-29
**Issue**: #28 (Phase 1 testing: Reference fixture generation + provenance ADR)

This ADR records the provenance, regeneration procedure, and tolerance
policy for the three Witchcraft-produced reference fixtures committed
under `Tests/Fixtures/`:

| File pair                          | Source                  | Purpose                                                 |
|------------------------------------|-------------------------|---------------------------------------------------------|
| `reference_centroids.{bin,json}`   | Rust Witchcraft (Q4K GGUF) | Verify Swift k-means on shared float inputs            |
| `reference_residuals.{bin,json}`   | Rust Witchcraft (`packops.rs`) | Verify Swift Q4 codec encoder/decoder parity            |
| `reference_embeddings.{bin,json}`  | Rust Witchcraft (Q4K GGUF) | Cross-stack embedder parity (FP32 CoreML vs Q4K GGUF)  |

These are distinct from `xtr-base-en.embeddings.{bin,json}`, which is
the **PyTorch** reference produced by `scripts/convert-xtr-to-coreml.py`
and used by `T5CoreMLEmbedderTests.fixtureParity` to validate
CoreML-against-PyTorch (≥0.999 mean cosine per row). The fixtures listed
above target a different parity gate: **Swift native code against the
upstream Rust implementation**.

---

## (a) Pinned Witchcraft commit

```
WITCHCRAFT_COMMIT=6ad59e51cfc89bcfb20756e3f05cf9429b7cb55f
```

Identical to the pin used by `scripts/witchcraft-fact-dump.patch`. Each
fixture's companion `.json` carries `provenance.witchcraftCommit`, which
must equal this SHA. A mismatch is a stale-fixture signal and triggers
regeneration (see (e)).

The pin is recorded in this ADR rather than in `Cargo.toml` because the
generator is a **patch against upstream Witchcraft's `src/tests.rs`**,
not an external Cargo binary — see (b).

---

## (b) Why a patch instead of a Cargo binary

The original spec called for a Cargo binary at
`tools/witchcraft-fixture-export/` linking Witchcraft as a git
dependency. That path is closed: Witchcraft's `kmeans()`,
`to_q4_bytes()`, `from_companded_q4_bytes()`, and the bucket-centroid
SQLite accessors are `pub(crate)` and unreachable from an external
crate. Publishing them upstream is an open-ended maintenance ask for a
one-shot fixture set.

The chosen alternative, `scripts/witchcraft-fixture-export.patch`, adds
three `#[ignore]`d tests inside Witchcraft's own `src/tests.rs`. From
that location the crate-private items are directly callable, the
existing `FACTS` / `make_device` / `Embedder::new` constants and
helpers are reused verbatim, and the regeneration story mirrors the
already-documented `scripts/witchcraft-fact-dump.patch` workflow.

Each test prints two stdout sections per fixture, framed by markers:

```
---SWITCHCRAFT-<NAME>-JSON-BEGIN---  …JSON metadata…  ---END---
---SWITCHCRAFT-<NAME>-BIN-BASE64-BEGIN---  …base64 of .bin payload…  ---END---
```

The runner (`scripts/README.md`) extracts the JSON region directly and
base64-decodes the binary region into the committed `.bin`.

---

## (c) Regeneration procedure

See `scripts/README.md` for the full step-by-step. Summary:

1. Clone Witchcraft, `git checkout $WITCHCRAFT_COMMIT`.
2. `make download` to fetch the ~62 MB Q4K GGUF + ~2 MB tokenizer/config
   into `assets/`. The model is **not committed** to either repository.
3. `git apply path/to/scripts/witchcraft-fixture-export.patch`.
4. Run each `#[ignore]`d test with `WITCHCRAFT_COMMIT` set, capture
   stdout, extract framed JSON and base64 sections, write to
   `Tests/Fixtures/reference_<name>.{bin,json}`.

The fixtures are intended to be regenerated on a **single canonical
machine** and committed once. They are NOT regenerated by every
contributor — Metal-backed GGUF inference on Apple Silicon is not
bit-stable across runs, so per-contributor regeneration would produce
spurious diffs. Cross-stack tolerances absorb the run-to-run drift; see
(d).

---

## (d) Tolerance policy

Each fixture has an explicit per-test tolerance with a cited source.

### `reference_centroids.bin` — k-means parity

The fixture's `.bin` carries TWO regions in one blob:

```
[ inputs (rows × dims FP32 LE) ][ centroids (clusters × dims FP32 LE) ]
```

The companion JSON describes both regions with byte offsets. The Swift
parity test (`KMeansTests.referenceCentroidsParity`) runs
`KMeans.cluster` on the inputs region (identical floating-point inputs
Witchcraft used) and compares the resulting Swift centroids to the
reference centroids region.

**Tolerance**: for each Swift centroid, the maximum cosine similarity
against any reference centroid must be ≥ **0.99**. We use
"every-Swift-centroid-finds-a-reference-near-match" rather than a fixed
permutation because k-means cluster ordering is implementation-defined,
and we cannot share an RNG across Swift `SplitMix64` and Rust's `rand`
crate (different families).

The spec originally proposed ≥ 0.9999. We loosen to 0.99 because:
* Lloyd's iteration on the small 33-fact corpus converges to local
  minima sensitive to init order.
* Swift and Rust use different RNGs for centroid initialisation, so
  exact convergence is not achievable.
* 0.99 is tight enough to catch a structural bug in the k-means kernel
  while remaining stable across hosts.

A second test (`referenceCentroidsStructure`) asserts shape + L2-norm
within FP tolerance independently of any cross-stack run.

### `reference_residuals.bin` — Q4 codec parity

The fixture stores, per input vector: the input floats hex, the
Witchcraft-encoded Q4 bytes hex, and the dequantised floats blob.

* **Encoder parity**: `Q4Codec.encodeResiduals(input)` must equal the
  reference Q4 bytes **byte-exact**. Both implementations are FP32 per
  ADR 003(a) — identical arithmetic, identical bytes.
* **Decoder parity**: `Q4Codec.decodeResiduals(q4Bytes)` must MSE-match
  the reference dequantised floats with **MSE ≤ 1e-3**, the same bound
  enforced by the existing `Q4CodecTests.residualRoundTripMSE` test
  per ADR 003(a).

Byte-exact encoder parity is a stricter check than the round-trip MSE
bound and catches any divergence in the compander, quantisation, or
nibble-packing logic on its own.

### `reference_embeddings.bin` — cross-stack embedder parity

* **Tolerance**: per-token absolute diff ≤ **0.025** per dimension, per
  ADR 010(h).

ADR 010(h) calibrated this bound against the Switchcraft FP32 CoreML
output and Witchcraft Q4K GGUF output on the XTR-base-en T5 graph.
Matched-precision FP16-vs-Q4K is not achievable on this graph (T5
encoder body NaNs under FP16 compute, see ADR 010(c) amended in fix
#31), so 0.025 is the realistic measured FP32-vs-Q4K drift.

## (e) Regeneration triggers

Regenerate one or more fixtures when:

1. The Witchcraft commit pin (above) changes — typically a Witchcraft
   point-release that touches `kmeans.rs`, `packops.rs`, or the
   embedder.
2. The XTR model is upgraded (commit SHA in
   `xtr-base-en.embeddings.json` changes).
3. Switchcraft's parity tests start failing in a way that points at the
   reference data being stale rather than at Switchcraft regression.

The fixture's `.json` `provenance.witchcraftCommit` is the canonical
freshness signal — diffing it against the pin in this ADR is sufficient
to detect (1).

---

## (f) Why `SWITCHCRAFT_FIXTURES_PATH` was rejected

ADR 010(d) defines the asset-distribution policy: large binary assets
(the ~80 MB `.mlpackage`) are env-var-gated; everything else is
committed. Reference fixtures here are small (centroids ~3 KB,
residuals ~5 KB, embeddings ~30 KB), so they fall in the "committed"
bucket alongside `xtr-base-en.embeddings.bin` and
`xtr-base-en.tokenizer.json`. Introducing `SWITCHCRAFT_FIXTURES_PATH`
would split the convention without delivering any size benefit.

Tests load via `Bundle.module` exactly like every other committed
fixture in `Tests/SwitchcraftTests/Support/`.

---

## (g) Asset gating for the embedding test

The spec's "Tests must pass on a fresh checkout (no model, no env vars
set)" line holds for the centroids and residuals tests, which run on
committed FP32 inputs and need no model. It is **not achievable** for
the cross-stack embedding parity test, which has to run the CoreML
embedder against the same inputs Witchcraft processed. That requires
`SWITCHCRAFT_XTR_MLPACKAGE` per ADR 010.

`CrossStackEmbeddingParityTests` follows `T5CoreMLEmbedderTests`'s
`.enabled(if:)` gating convention and skips cleanly when either the
model or the fixture is missing. A fresh checkout therefore stays green:
the structural parity tests run; the model-dependent parity test
skips.

---

## (h) Soft contradictions vs the issue spec, recorded for posterity

The implementation deviates from the issue spec in two places, both
recorded above:

* **Generator placement**: patch under `scripts/`, not Cargo binary
  under `tools/witchcraft-fixture-export/`. Reason in (b).
* **Centroids tolerance**: ≥ 0.99 cosine, not ≥ 0.9999. Reason in (d).

The spec's intent (cross-implementation parity gates with
machine-readable provenance) is preserved; only the mechanics are
adjusted to fit Witchcraft's actual API surface and the XTR T5 graph's
measured precision behaviour.
